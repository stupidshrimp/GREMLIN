Standards and Documentation

How GREMLIN calculates analysis and metrics.

Use the tabs below as a plain-language reference for what each number means, the formula behind it, and which GREMLIN data fields feed the calculation.

Metrics Dashboard

The Metrics dashboard uses corrective work orders for the selected assets and dates. A work order is included when its final class is corrective. If a final class has been saved, that final class wins. If no final class has been saved yet, GREMLIN can use the corrective-candidate flag as a fallback.

Work Order Count

Work Order Count = count of included corrective work orders

This is the number of corrective work orders found in the active date window.

Total Downtime

Total Downtime Hours = sum of downtime_hours

GREMLIN adds the downtime hours from each included corrective work order. Blank downtime counts as 0.

MTTR

MTTR = Total Downtime Hours ÷ Work Order Count

Mean Time To Repair shows the average downtime per corrective work order.

MTBF

MTBF = hours between first and last dated corrective work order ÷ number of gaps

GREMLIN sorts dated corrective work orders from oldest to newest. If there are fewer than two dated work orders, MTBF is shown as Data Required. This is calendar time today, not operating-hour meter time.

Percent Change

Percent Change = (Current - Baseline) ÷ Baseline × 100

The selected date window is split in half. The earlier half is the baseline and the later half is current. If baseline is zero and current is above zero, GREMLIN treats the change as new activity instead of a finite percent.

Risk Score When Baseline Exists

Risk = 40% downtime score + 25% work-order score + 25% MTTR score + 10% repeat score

This formula is used when at least one selected asset has baseline records in the first half of the date window. Increases from baseline raise the score. A doubling, or activity appearing from zero, scores 100 for that component. No increase scores 0. The final score is capped from 0 to 100.

Risk Score Without Baseline

Risk = 45% relative downtime + 27.5% relative work-order count + 27.5% relative MTTR

If no selected asset has baseline records, GREMLIN switches to relative scoring. Each component is min-max ranked against the selected assets, blended with the weights above, and capped from 0 to 100. Repeat failures are not included in this no-baseline formula.

Risk status

High: 70 or above. Medium: 40 to 69.9. Low: below 40.

Weibull Analysis

Weibull analysis uses dispositioned failure and reset events for the selected asset and failure group. The goal is to estimate how failures behave over life hours.

Observation Life

Life Hours = hours from interval start to interval end

Interval ends come from included failures, approved PM reset events that are still marked as Weibull candidates, or the analysis cutoff for right-censored current life. GREMLIN uses schedule-adjusted weekday hours for these life intervals.

Failure Indicator

Failure = 1 for INCLUDED_FAILURE; 0 for right-censored observations

At least one included failure and at least one positive life-hour observation are required to fit Weibull parameters.

Beta (β)

β is the Weibull shape parameter estimated by maximum likelihood

β below about 1 suggests early-life or defect-driven failures. β near 1 suggests random failures. β above about 1 suggests wear-out behavior.

Eta (η)

η = (sum of all life_hours^β ÷ number of failures)^(1 ÷ β)

η is the characteristic life scale. It is useful for planning and comparing populations.

Reliability Curve

Reliability at time t = exp(-((t ÷ η)^β))

The plotted failure probability is 1 minus reliability.

MTTF, B10, and B50

MTTF = η × Γ(1 + 1 ÷ β)

B10 = η × (-ln(0.90))^(1 ÷ β); B50 = η × (ln(2))^(1 ÷ β)

MTTF is mean life. B10 is the life where 10% are expected to fail. B50 is the median life.

Pareto and Trend Analysis

These views use included failure records that have a failure mechanism and are still marked for Weibull/event-processing inclusion. They help explain which mechanisms create the most activity and downtime.

Pareto Failure Count

Failure Count = count of included failures marked as Weibull candidates in the mechanism

Each included failure is grouped by its failure mode and failure mechanism.

Pareto Downtime

Downtime Hours = sum of downtime_hours for the mechanism

Mechanisms are sorted by downtime first, then by failure count.

Cumulative Percent

Cumulative Percent = running downtime total ÷ total downtime × 100

This shows how much of the total downtime is explained as you move down the Pareto list.

Monthly Trend

Monthly Count = count of included Weibull-candidate failures in each YYYY-MM bucket

GREMLIN buckets records by work-order date. Missing months are filled with zero so the line does not skip gaps.

Fastest Growing

Growth = failures in most recent 3 months - failures in previous 3 months

This is only calculated when there are at least six months of trend data.

Downtime Drivers

Average Downtime = total downtime ÷ work order count

Downtime-driver views also group events into simple bins: 0–1, 1–4, 4–8, 8–24, and 24+ hours.

Where the Numbers Come From

GREMLIN starts with raw CMMS task data, maps it into analysis fields, then uses the current disposition decisions saved by users.

Source System

Records come from Limble CMMS imports stored in GREMLIN.db. The original raw record is kept, and mapped fields are derived from it.

Asset Filter

Asset = mapped_cmms_record.asset_number

Most screens only use records matching the selected asset number.

Work-Order Date

WO Date = completed_date_final, else start_date_final, else created_date_final

GREMLIN uses the best available date in that order for metrics, Pareto drilldowns, and trends.

Downtime

Downtime Hours = mapped downtime converted to hours

For the documented metrics, Pareto, trend, PM-effectiveness, and downtime-driver calculations, blank downtime is counted as 0 hours and negative downtime is clamped to 0 before GREMLIN sums, averages, ranks, or displays downtime.

Included Failures

Included Failure = current disposition is INCLUDED_FAILURE and include_in_weibull_candidate = 1

Failure-mode and failure-mechanism fields come from the current disposition for that work order. If the Weibull-candidate checkbox is cleared, the record is excluded from Weibull, Pareto, and trend calculations even when its category is INCLUDED_FAILURE.

Approved PM Resets

Approved Reset = INCLUDED_PM_RESET_EVENT and APPROVED_RESET and include_in_weibull_candidate = 1

Approved PM resets can start a new life interval for Weibull analysis when a reset target is selected. If the Weibull-candidate checkbox is cleared, the PM is documented as an approved reset decision but it does not reset the Weibull life interval.
