How GREMLIN Works

GREMLIN reads maintenance records from Limble, lets people classify them, and turns them into metrics and analyses. This tab explains how the pieces fit together, from the data underneath to the pages, accounts and tools on top.

{% call std.figure("S1", "How records move through GREMLIN. Limble is the system of record; GREMLIN keeps a copy, adds the decisions people make about each record, and calculates the metrics and analyses from those every time a page asks, apart from Weibull fits, which are saved when an editor runs one.") %} {% endcall %}
{% call std.doc_card( "site-data", "From Limble to GREMLIN", "Where the records come from, how often they are refreshed, and what happens to them on the way in.", eyebrow="Data") %}
  • Limble is the system of record. GREMLIN reads from Limble and never writes back to it, so most corrections are made in Limble and flow in with the next sync. Three kinds do not: a work order moved to another asset stays under the asset it was first stored under, a field cleared in Limble keeps its old value here (dates and the four instruction boxes excepted), and a task deleted in Limble stays in GREMLIN.
  • The Limble sync runs every night as a scheduled job. An administrator can also start it from the Developer area when a correction has to show up sooner. Each run pulls every task (work orders and PMs) and every asset. It also reads the Area Affected, Condition, Cause and Action boxes from the instructions of completed tasks it has not read yet or that changed since, up to 500 tasks per run by default, newest first, working back through the history.
  • Raw records keep every field Limble sent for each task, with GREMLIN's own additions stored alongside (the asset number, its place in the hierarchy, readable UTC dates and the four instruction boxes), so the mapping can always be redone. Template tasks, which are PM and work order definitions rather than events, are left out.
  • Mapped records copy the fields GREMLIN works with into columns of their own: the asset number (Limble's asset ID, or the number older records used for the same asset), the asset's name and place in the asset hierarchy, the created, start and completed dates (stored in UTC), status, Limble's task type, downtime converted from seconds to hours, the description and completion notes, and the Area Affected, Condition, Cause and Action boxes.
  • The mapping also guesses a record class for every record; the next card explains how, and why a person's call replaces it.
  • The mapping is rebuilt by itself whenever its rules change, and editors can catch it up from Configuration with Refresh CMMS mapping, which maps any records imported or changed since the last mapping.
  • GREMLIN keeps its data in four SQLite files, so a backup of GREMLIN.db alone is not enough:
    • GREMLIN.db: the Limble records, dispositions, failure modes and mechanisms, Weibull results and the Weibull schedule register, and the availability configuration, goals and overtime.
    • accesscontrol.db, beside GREMLIN.db: the accounts and their login and change history.
    • auxillary.db, in the GREMLIN Global DB folder on the shared drive: the bug reports, one list for every installation.
    • PM_Calendar_local.db, beside GREMLIN.db: the PM Task Tracker's copy of PM tasks. It holds only what it pulls from Limble, and every pull fetches all of it again.
    Back up the first three. Those are their default places; an installation can move any of the four, and the Developer area shows where the first three are.

The automatic record class

As each record is mapped, GREMLIN reads its Limble type, its name, its request title and description, its completion notes and its tags, and takes the first of these rules that matches:

  1. Parts order: the text talks about ordering, delivering or stocking parts.
  2. Project work: the text mentions a project, an upgrade or an install.
  3. PM: Limble type 1, a PM code such as "- M -" or "- Q -" in the name, or the word "pm" in the text.
  4. Corrective work order: Limble type 6 (a work request), or repair words such as leaking, broken, fault, failed or replace.
  5. Inspection: inspection words with no repair words.
  6. Unknown: none of the above.

It is only a starting guess

The word "pm" also matches the clock in return-to-service notes such as "RTS at 4:30 PM", so real breakdowns can be guessed as PMs. That is why availability's hours and its Exclude PMs switch ignore the guess, which only names the non-PM segments of its stacked bars, and why a class a person saves on the Disposition page replaces it in every metric and analysis.

Dispositioning

Editors open Disposition and pick an asset: its work orders are listed on the left, and the one picked opens on the right with its request, notes and narrative above the fields, and a link to open it in Limble. The bar above them switches to the disposition alone across the page, or the list alone. Each work order takes a category, and then where it failed (sub-asset), what (component, and the part within it when it was one), how (failure mechanism, mode and cause), what was done (action), how sure the record is (evidence), its record class, and a note; Save & next moves down the list. Saving keeps the previous decision as history, and the list says who last edited each one. The list can be narrowed to the work orders not reviewed yet, to those carried over from the REL categories that still need confirming, or to those the helper dispositioned, and the same work orders can be downloaded to Excel, filled in there and uploaded.

Every code field is a search: type any part of a code, its name or its description. The code lists the fields offer (components, parts, mechanisms, modes, causes and actions) belong to the team and are edited from the Disposition page, or added straight from a field when nothing on the list fits; a code that is retired keeps reading on the records that use it. The disposition helper can fill a work order in, and checks every new code for one already listed: see The disposition helper. What each category means for the analyses is on the Analysis tab, in What every analysis reads.

The disposition helper is not a chatbot. It is a set of text-matching rules and statistics learnt from the dispositions your team has already made, and it runs on the GREMLIN server: no work order text leaves the plant. Where the server has the optional small language model installed, it also recognises wording that means the same thing in other words. It does two jobs: it fills in a work order's disposition for an engineer to check, and it checks every new code against the codes already listed.

Filling in a disposition

For each field it fills (category, sub-asset, component, failure mechanism, failure mode and action) the helper weighs two kinds of evidence.

  1. Similar work orders vote. Every work order already dispositioned is indexed by its words and the ideas read from them. Common words such as "replaced" or "PM" count for little; specific ones such as "S09" or "flame rod" count for a lot. The 25 work orders most like this one each vote for the codes they were given, weighted by how alike they are. A vote from the same asset counts 1.5 times; one carried over from the REL categories counts 0.6 times, since it was made under the old categories; one from a work order of another category counts for less. If "dry-off tripped" has been coded S09, Burner, Signal fault a dozen times, the thirteenth is suggested the same. With the language model installed, how alike two work orders are is 80% their wording and 20% their meaning.
  2. What the work order says outright. A word from the code lists, or from the helper's list of maintenance phrases, is evidence on its own: "clogged" points to Plugged, "won't light" to Fail to start, "replaced" to Replace. It reads negation, so "no leaks found" counts against Leak. The sub-asset is read from its number ("S09"), its name, or the asset the work order was logged against. This is what carries a work order unlike any seen before, or a code nobody has used yet.

The two are blended by how much of each there is. When the votes and the wording agree the helper is sure; when they disagree, or there is little of either, it is not, and a single weak vote never reads as sure. The failure cause then follows the mechanism's default unless the work order and its look-alikes agree on another, a PM reset is given the items it renewed, and the evidence is Explicit when the work order names the item and its condition, Inferred otherwise. Every suggestion goes through the same rules a save does.

What the percentage means

The helper re-reads up to 400 of the work orders the team has already decided, each as if it were new (without itself in the index), and counts how often a suggestion at each score matched the engineer's decision. That count is the percentage beside each field: 90% means nine in ten suggestions that scored like this one were right. Until 40 work orders have been decided it cannot measure itself; it then shows 85% of its raw score, marked as an estimate, and a backlog run is refused. How accurate is it? on the Disposition page shows the same measurement, field by field.

What you see
  • The Auto-disposition switch on the Disposition page turns it on. Each work order you open is read, and every field the helper is at least 50% sure of is filled in, with its percentage beside it. A field it is less sure of shows its suggestion beside the field as a button.
  • A panel above the fields says what it read, the alternatives it weighed, and the similar work orders that voted, each with how alike it is.
  • It never fills over an engineer's disposition; it only offers its view beside each field. Nothing is saved until you save, and a save keeps the suggestion it was made from, so the helper can be measured in real use.
  • Auto-disposition the backlog… previews, then saves, the not-reviewed work orders it is at least 90% sure of (the bar can be lowered, not below 60%), up to 1,000 a run. Each is marked Auto with a review flag, listed under Show: Auto-dispositioned until an engineer saves it, and the whole run can be undone at once.
  • Possible duplicate work orders: a work order on the same asset that reads at least 60% the same and was logged within 3 days is pointed out, with a button to mark this one a duplicate of it. The helper never makes that call itself, nor chooses Held.

Its limits

It learns only from the team's own dispositions, so it gets better as more are made, and a short or oddly worded work order gets a low percentage. It suggests a component but not yet a part.

Checking new codes for duplicates

Before any code is added, on any list (component, part, failure mechanism, mode, cause or action), the helper compares its name and description with every code already on that list and scores each from 0 to 1. Codes scoring 0.45 or more are shown, the five best first, each with why:

What the duplicate check reads as alike
Reason shownExampleScore
The same name, ignoring capitals and punctuation"O ring" and O-ring1.0

Shares the words, plurals read as one: a word few codes use counts for most, the description for less than the name"Hydraulic pumps" and Pump, hydraulicup to 1.0
One of its names: a part of a name written with slashes, or for a component one of the helper's maintenance phrases"Air compressor" and HVAC / compressor / chiller0.75

Where it runs:

  • On the Disposition form and in the Code lists dialog, the look-alikes appear as the name is typed, each with Use this (or Open it in the dialog). While any show, the button reads Add it anyway.
  • On the server, for every new code however it comes: one like a listed code is refused unless the person adding it has seen the look-alikes and chosen Add it anyway, so an old browser tab can't add one unseen.
  • Between components and parts: a new part that is a listed component under another spelling ("Electric motors" for the component Electric motor), or a new component that is a listed part, is asked about too, and the form offers Use as the component. A part that only shares a word with a component, such as "Compressor filter", is what a part is and is not asked about.
  • In the code-list workbook (Developer > Code lists), which can't ask "add it anyway": a new code scoring 0.85 or more (a plural, a slip of the keys, the same words reordered) refuses its row, as does a part that is a listed component, and the row says to add it from the Code lists dialog if it really is different. Each new row is also checked against the new rows above it. A new code merely like a listed one is added and listed after the upload for someone to check.

Retired codes are compared too, marked Retired, so a code retired once is not added again under its own name. The check stops new duplicates only: look-alikes already on the lists stay until someone retires one of them.

{% endcall %} {% call std.doc_card( "site-changes", "When the numbers change", "What updates a number, and when.", eyebrow="Freshness") %}
  • New Limble records, and most corrections, reach GREMLIN.db with the nightly sync, or sooner if an administrator runs one; From Limble to GREMLIN lists the corrections that do not carry over. The PM Task Tracker keeps its own copy, refreshed when an editor presses Sync from Limble on that page.
  • Availability is recalculated every time the Metrics page loads, from the configuration as it is at that moment. See Asset availability by month.
  • The trend, downtime driver and PM effectiveness analyses read the current dispositions every time they load.
  • Weibull results are saved snapshots, one per failure group. Run the analysis again to include dispositions saved since; the new run replaces the group's previous one and any adjusted parameters saved with it. Changing a disposition from the Weibull data table re-runs it straight away. Unless a cutoff date is entered, a run censors the current life at the last completed Limble import, so a sync before running brings the lives up to date too. A result saved under an earlier version of the Weibull method, or counted on a schedule its asset has since been moved off, says so, and has to be run again before it can be reported.
  • Configuration changes to schedules, group membership and linked downtime recalculate every month of availability. Goals and overtime change one month at a time.
