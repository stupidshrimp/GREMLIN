    Dispositioning explained

    How dispositioning on Excel works

    Excel is the offline version of the table on this page. Download the entries for the asset you selected, fill in the disposition columns in Excel, then upload the same workbook to save them all at once. Nothing reaches the database until you upload it back.

    Download Excel → Fill in the disposition columns → Disposition via Excel
    1. Select the asset and record type first. The workbook is built from the Asset Number and Record Type chosen in Step 1, and it holds every eligible entry for that selection; the Rows selector, the search box, and the page you are on do not narrow it.
    2. Click Download Excel. You get <asset>_wo_dispositions.xlsx (or _pm_ for PM reset events). The first sheet is one row per record; the second sheet, Lookup Lists, feeds the dropdowns, so leave it in the file.
    3. Fill in the disposition columns. They are the last columns on the sheet, and most of them are dropdowns:

      Both record types

      • disposition_notes: free text. Required for HELD_AMBIGUOUS and EXCLUDED_MIXED_CONTAMINATING.
      • disposition_category: dropdown.
      • record_class: dropdown.
      • include_in_weibull_candidate: set this to TRUE on every row the analysis should use. It arrives FALSE on any row nobody has dispositioned yet, and the import keeps whatever the cell says, so a row left at FALSE saves fine and is still left out of the Weibull.

      Work orders

      • failure_mode and failure_mechanism: pick from the dropdown, or type a brand-new name and it is created for this asset on import. A WO becomes Weibull-usable only as INCLUDED_FAILURE with a failure mode and include_in_weibull_candidate at TRUE.

      PM reset events

      • pm_reset_decision, reset_target_failure_mode, reset_target_failure_mechanism, pm_reset_renewal_rationale. A PM becomes Weibull-usable only as INCLUDED_PM_RESET_EVENT with APPROVED_RESET, a reset target, a rationale, and include_in_weibull_candidate at TRUE.
    4. Leave the rest of the sheet alone. mapped_record_id is how each row finds its record: never edit it, delete a row, or add one. The task, date, downtime, note and failure-narrative columns are read-only; edits there are ignored on import, so the workbook can never overwrite what the maintenance team recorded in Limble.
    5. Click Disposition via Excel and choose the file. Rows are matched back by mapped_record_id. Every row whose values differ from the saved disposition is written as the current one, with the same result as editing it here and clicking Save Dispositions. Rows that already match are skipped. What the workbook is compared against is the database, not anything half-typed in the table below: the page reloads on a successful import, so it asks before discarding unsaved edits, the same way paging and the selectors do.
    Worth knowing

    Changing a failure mode or mechanism? Clear both of that row's failure_mode_id and failure_mechanism_id cells (or the reset_target_…_id pair for PMs). The id columns win whenever they are filled in, so a new name typed beside an old id is read as no change at all.

    Moving a row to another failure mode moves its mechanism too. Clearing the ids is not enough on its own; the mechanism has to be one that belongs to the new mode, so pick one of its mechanisms, type a new name for it, or leave the mechanism cell empty. A mechanism carried over from the old mode is refused, and refusing one row is refusing the file.

    PMs cannot invent taxonomy. A reset target has to be an existing work-order failure mode/mechanism, so choose those from the dropdown. Work orders are the only place a new mode or mechanism can be named.

    One wrong row stops the whole import. Nothing at all is saved when a single row is refused, whether it is a mapped_record_id that does not belong to the selected asset and record type (usually a workbook downloaded for a different one), or a mechanism sitting under the wrong failure mode. Fix that row and upload the file again.

    A workbook is a snapshot, and uploading it does not merge. Each row is compared against the database as it stands when you upload, not against the sheet as it was downloaded. So if somebody else dispositioned one of these records while your copy sat on your desktop, your untouched row still counts as a difference and puts the older values back over theirs. Download a fresh workbook if yours has been sitting around, and try not to have two people on one asset at the same time.

    Downloading is open to everyone; importing writes, so it needs an editor account. Uploading the same file twice in a row is harmless: the second pass finds the database already matching.
